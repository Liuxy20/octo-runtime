# 评分口径与结论

复评 **96/100**。这是对任务拆解、方案明确程度和验收可执行性的工程判断，不是实现完成率、
可靠性保证或第三方认证。没有因代码未写、测试未跑而扣分，也不通过添加条目数量提高分数。
本轮只修改规划文件，M0–M6功能仍待实施。

最新CLI约束已同步：executor-kernel与channel-gateway分别提供uninstall/install/start/restart/stop/run，
两组操作互不连带；T07和A24按2×6动作验收。7份文档的结构/链接/验收映射和命令一致性检查通过，
全仓知识检查仍仅有基线14处失效链接；未执行运行代码、平台或真实业务验收。

用户已明确旧daemon直接改名拆分或删除重写，因此原评估中的“迁移路径”收敛为源码去向与接入改动；
兼容命令、旧服务自动迁移、双轨交付不再是要求，也不因删除这些范围扣分。

## 原10分缺口的逐项处理

| 原扣分 | 已细化内容 | 恢复 / 保留 | 依据 |
| --- | --- | --- | --- |
| 拆解1分 | M3a不含宿主proxy，M3b独立实现并验收；失败不退回同进程Extra | +1 / 0 | plan M3、test-execution T04/T05。 |
| 技术4分中的接口2分 | 四种能力对象、工厂名、CleanupResult、方法表、RPC外层实例ID、ACK未知处理已固定 | +1 / 1 | design D1–D4；剩余Schema跨语言交接风险见下。 |
| 技术4分中的代理2分 | call/cancel/result/settled、epoch、真实占额、deadline、字节/队列、断连和关闭已固定 | +1 / 1 | design D5；剩余同步宿主函数故障域风险见下。 |
| 验收3分 | 明确测试文件/fixture、五组竞态步骤、Windows pipe/任务执行入口与缺平台处理 | +2 / 1 | test-execution全表及F01–F05。 |
| 切换交付2分 | 删除旧架构的明确决定，24行源码去向、公开入口/配置/服务ID与产物负向检查 | +1 / 1 | changes与A27；维护中外部Host调用改动仍需具名交接。 |

## 剩余4分，不以缺少实现或测试结果代替理由

1. **wire交接1分**：当前有选定结构与行为，但#51共享Schema评审仍可能发现null/省略、native payload或版本协商边缘差异；M0须用同一正反fixture消除，不能双方各写一套。
2. **宿主回调故障域1分**：任意同步函数可阻塞宿主，代理不能提供线程隔离；方案已明确限制和有界等待，但实际接入必须判断自身函数是否满足主循环响应前提，不能作透明兼容承诺。
3. **平台测试设计1分**：Windows受管后代确认与Linux user manager的可用性受运行会话影响；已指定真机补证据入口，但平台后端可能需要进一步细化可观察判据。扣的是环境适配不确定性，不是测试未执行。
4. **外部接入交接1分**：本仓Node SDK示例已可明确实现，#50维护的第三方Host尚未在本任务确定具体调用点及版本；不能用通用四例推定所有产品迁移工作量。

下一步可直接按M0把选定设计落成Schema/声明与合同fixture；不再需要为接口命名、旧daemon保留策略或proxy主要机制重新立项讨论。
