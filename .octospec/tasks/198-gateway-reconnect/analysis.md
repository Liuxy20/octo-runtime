# 已确认的阻断路径

事故构建 `13f05e0139ae` 和本次基线 `f0bacb0` 的路径一致：`WukongConnection` 收到 kind 9 → 生成 `ImConnectionError(code, false)` → `ImRuntime.#lostConnection` 进入 failed → 关闭旧 connector，但不调用 `#scheduleReconnect`。因此没有 attempt，并非已经安排了计时器却没有执行。原测试甚至明确要求 reason 12 不重试，旧规则也将其作为永久失败；这是需要纠正的恢复策略，不能用原测试通过证明用户场景已修复。

用户进一步澄清触发是直接断网，主要是单实例，并以服务滚动更新说明服务端主动断开不等于永久拒绝。最终合同：服务 SLA 问题默认重试；只有有明确依据的认证、封禁、权限、配置或协议错误才能停止。未知服务端原因不构成不可恢复证据。连接恢复和执行重放分开，恢复不重提旧任务。

# 同类路径及结果

| 路径 | 原行为 | 本次处理 |
| --- | --- | --- |
| 已上线后任何 DISCONNECT | 所有原因都永久 failed | 明确永久拒绝之外默认退避，包括 0、12 和新增码 |
| CONNACK 非成功 | 所有握手失败都永久 failed | 同一明确永久拒绝集合；系统/Token 查询/节点/限流/未知服务错误默认退避 |
| CONNACK 前 DISCONNECT | 提前命中 IM_HANDSHAKE_REQUIRED | 先处理断开，保留原因与恢复资格 |
| AUTH/REGISTER HTTP | 仅 429、5xx 恢复；408、409 等永久失败 | 超时、冲突、过早请求、过载及未分类服务故障默认重试；仅明确请求/资源/鉴权/协议错误停止 |
| 未分类连接异常 | 统一永久失败，外部依赖瞬时失败也会卡死 | 未分类默认重试；保留明确本地身份、配置、协议和资源所有权终态集合；原始私有异常仍只显示 IM_CONNECTION_FAILED |
| HTTP 重定向 | fetch 的 redirect:error 将状态折叠成网络异常 | manual 取得状态并明确失败，不跟随、不转发凭据 |
| 普通 socket close / WS error / 连接超时 | 可重试 | 保留，用多轮完整链路验证 |
| 心跳静默检测 | 每 25 秒检查，超过 90 秒无包才失联 | 未调整；不是 20 秒故障检测保证 |
| 回收未完成或失败 | 未完成一直等待，失败停止 | 保留单连接所有权；已有回归明确验证这条边界，不用超时后强开第二条连接 |
| 宿主凭据 Promise 永不完成 | 连接准备等待 | 本次未新增依赖执行器或超时配置；宿主按既有 signal 合同返回/取消 |

永久原因码集合是 2（认证）、4（黑名单）、8/9（消息密钥/载荷协议）、11（不允许发送）、13（白名单）、19（封禁）、20/21/23/27（头/客户端密钥/类型/版本协议不支持）。其他合法 CONNACK/DISCONNECT 原因码默认重试。基于本地 `octo-im@613fc2b2b3a4c23054385ee3f8238fc44a8f68e7` 的 `pkg/protocol/frame/common.go` 核对；这不是事故部署版本证明。

HTTP 明确终态集合为 400/401/403/404/405/407/410/411/413/414/415/416/417/422/426/428/431/451；不跟随的 3xx 按地址/协议配置错误处理。408/409/421/423/425/429、全部 5xx 和未分类服务状态默认恢复，Retry-After 继续有效。正常业务 API、执行错误和消息投递不使用这套连接重试策略。

# 为什么不是 20 秒

退避是旧连接回收完成后等待 5 秒、10 秒、15 秒，此后每 15 秒，成功后归零。它不包含：失联发现、旧连接回收、宿主取凭据、AUTH、REGISTER 和 WS 握手。AUTH、REGISTER、握手各有自己的 15 秒上限，不能把它们理解为一次恢复共有 15 秒。Retry-After 还可以延长等待。

静默丢包未产生 close 时，以最近收到完整帧/心跳包时间为准，超过 90 秒才在下一次 25 秒检查中 terminate；事件循环正常推进时约为最近包后 90–115 秒检测，具体受定时器调度影响。休眠暂停事件循环，没有 wall-clock 硬时限；唤醒、网络恢复、发现失联与连接成功是四个不同事件。

# 现场证据边界

本地服务端源码把 reason 12 命名为 ReasonConnectKick；路由替换和 Token 更新均可发它。这不能证明用户存在第二实例，也不能证明直接断网为何在实际部署产生 12。客户端永久停重试的链路已经确定，可按用户明确的恢复策略修复，不等待对“争抢”的假设论证。

本次自动化用本地 HTTP/WS 注入原因码、断开连接与服务 503，未改变本机网络，未重启用户服务，未向测试站发消息，未做真实服务器滚动发布。CLI/SDK fixture 的成功不冒充现场合盖、断网、真实 DM/群或服务端部署验收。已知不包含跨进程同 Bot 仲裁；按照用户决定，不为主要单实例场景引入该机制。
