# 目标与决策

用户报告直接断网后没有 retry attempt，要求独立 worktree 按 octospec 处理，并明确大多数场景仅有单实例，不应为假设的连接争抢阻断恢复。Issue #198 的保留日志显示六个 `IM_SERVER_DISCONNECTED_12`，未出现重试。基线为最新 `origin/main@f0bacb0`，分支 `codex/198-gateway-reconnect`。

业务目标是恢复已配置 Bot 的连接；决定权属于 Gateway 渠道，不属于 Kernel、Provider 或宿主服务管理器。输入仍为宿主已有 Bot 配置与凭据。最先阻断恢复的是 WuKong 传输对所有 DISCONNECT、失败 CONNACK 一律 `retryable=false` 的分类。公共输入、服务工厂与进程拓扑不变：CLI 服务进程和 SDK 调用进程原生装配同一 Gateway，由 Gateway 持有 socket、回收和单一退避计时器。

用户本轮决定覆盖旧规则“reason 12 未确认部署语义前永久失败”的处理。reason 12 进入现有恢复，不新增多实例仲裁、锁或抢占检测；真正多实例同 Bot 的协调不由本次客户端修复保证。仍须正常鉴权，认证、身份和协议非法保持失败。

# 关键合同与同类检查

- 合法 DISCONNECT 默认重试（含 reason 12、0 及未知码），只将明确认证/权限/封禁/协议错误码 2/4/8/9/11/13/19/20/21/23/27 保留终态；握手前的 DISCONNECT 使用相同分类，不能误报 IM_HANDSHAKE_REQUIRED。CONNACK 同样默认重试，只使用同一明确终态拒绝集合，不将认证失败 2 误当成 Token 查询服务故障 14。用户最终明确：服务 SLA 问题默认重试，未知服务端码不是永久拒绝的证据。用户进一步以服务滚动更新明确要求按断开与拒绝分别处理，不能只补 reason 12 白名单。
- AUTH/REGISTER HTTP 仅明确认证、配置/资源及请求协议错误停止；408/409/421/423/425/429、5xx 及未明确永久性的错误默认重试，继续尊重 Retry-After。重试重新走验证、注册与握手。
- 旧连接回收后等待 5/10/15/15…秒，Retry-After 可延长；不能承诺断网后 20 秒内必定连接成功。静默断网仍由既有每 25 秒检查、90 秒无包阈值检测，恢复总时长另含清理和认证握手，系统睡眠时 timer 不运行。
- 未分类的连接依赖异常默认恢复，明确本地认证/配置/协议/资源所有权错误仍停止。HTTP 重定向保留状态、不跟随，不将其误报网络故障。
- disconnected 日志记录实际目标 state，永久失败不能只留一个含糊断线事件。任务不重放，迟到回调、主动关闭、连接单一所有权继续受现有状态机保护。
- 清理卡住/失败、凭据回调永不完成也可能挡住恢复；分别记录边界，不用跳过回收或猜测凭据来启动第二连接。

# 验收

1. 旧构建跑新增分类回归应失败；修复后真实 loopback WS 覆盖暂态/终态 CONNACK 与 DISCONNECT、同包成功后断开及半开超时。
2. 状态机覆盖连续暂态失败、精确 5/10/15 秒退避、成功归零、停止与迟到事件、清理失败和 Retry-After。
3. CLI 与原生 SDK 通过真实本地 HTTP/加密 WS/Kernel worker 链路，覆盖普通断开和重复 reason 12 后的新消息执行与回复，服务身份不变、旧任务不重提、连接数符合预期，完整重试日志可观察。
4. build/typecheck、lint、格式、命名与相关测试通过；OKF 校验区分主线已有错误。
5. 上述 loopback 是自动化 fixture，不是线上测试、真实断网或合盖验证。实际服务端为什么发送 12、原事故部署和真人 DM/群回归另列未验事实；不据此声称 P0 全部验收或已修复用户安装版本。
