# 决策与范围

用户在 Issue #234 本地验收中发现：创建 `hellowlrd.md` 后，先发送“讲一个冷笑话。”，再 mention Bot；自动 history 同时带回该 Bot 上轮文件卡、带附件链接的文字回复和用户的新消息。用户要求保守处理，宁可少量重复，也不能误删当前模型尚未获得的历史。

用户已经授权修改代码、code-review、build 和全局安装，并明确：**只在 channel-gateway 内处理**。本项产品改动限定 `packages/octo-runtime-extra-channel-gateway/**`，专项验证放 `test/manual/`；不改 Executor Core、Kernel、公共协议/生成源、Provider Adapter 或其他 Extra，不新增宿主接口、配置开关、模型提示词或 GitHub CI。某条路径无法在 Gateway 内证明安全，就保留原历史，不为优化扩大下层合同。

这是对当前会话已覆盖输出的有限排除，不是全面去重。首轮的“全部历史”始终指既有同频道窗口内的历史，仍受最多 20 条、8000 Unicode 码点和总 Context 预算约束，不变成全频道无限读取。

## 场景与保留策略

| 场景 | 自己 Bot 的历史消息 | 其他消息 |
| --- | --- | --- |
| 首轮、新逻辑会话、新 Provider 会话、reset/new 后 | 保留，不按 UID 或旧输出凭据排除 | 按原窗口保留 |
| 明确连续接续同一 Provider 会话，正常 delta | 仅排除能确认由该接续会话已有 assistant 内容覆盖的具体消息 | 用户及其他 Bot 的 gap 消息保留 |
| 待补边界重读、历史补位、bootstrap、连续性未知 | 保留，即使 UID 是自己或恰有旧 ACK | 按原补读合同保留 |
| fresh fallback、Provider 会话变化或恢复语义不明 | 使用未经过本项排除的历史；无法确保时不启用排除 | 保留当前 query 和必要 gap |
| 输出归属缺失、凭据过期/淘汰、迟到 ACK、进程重建、自定义 store 不具备所需原子能力 | 保留，不猜测已覆盖 | 保留 |
| 同代次自动/卡片重试 | 复用原冻结快照及恢复输入，不重新过滤 | 不重新采集或改变原材料 |

当前触发消息仍作为 query，不重复放 history。宿主显式提供的 history/其他 Context 完整保留，本策略只选择 Gateway 自动采集的 history 消息。不会递归删除他人引用或转发中的自身发言，也不会按同 UID 删除整段聊天。

## 实施前缺口

1. `application/context-gap.ts` 已记录最多 32 个 `localOutputSeqs`。当缺口跨度全部由这些位置解释时，可以跳过历史读取；但其中混入一条用户消息就会进入 delta。
2. `transport/contexts.ts` 读取整段后只按消息位置/ID及窗口筛选，没有逐条排除已知且被接续会话覆盖的自身输出，因此文件卡和回复又进入模型。
3. `localOutputSeqs` 证明本机有发送位置，不能单独证明是该 Provider 会话已保存的 assistant 正文。Gateway 的控制回复、错误提示、交互/进度卡、额外工具发送及新增交付事实不能据此一律删除。
4. `sessionId` 存在只表示持有恢复句柄，不保证本轮恢复成功。Codex 现有路径可能在 `turn/start` 后才发现原会话缺失并使用 fresh fallback；当前 Gateway 恢复输入主要补稳定/群规则，不能据此声称已恢复本项排除的历史正文。
5. 原历史缺失判断包含筛选数量差异，新增的主动排除不能直接套入该差异，否则可能错误生成 history.note。

## 排除资格：条件同时满足

- 本轮是正常增量接续：已建立的逻辑 session/generation、同 Provider 目标和原生会话归属明确；不是首轮、补位、未知基线或恢复路径。存在待补边界时一律不启用本项排除，不只保留下界之前的消息。
- 对具体消息有可验证的本机输出关联：同 Bot/Space/频道、同逻辑 session/generation、所属 Run 和 Provider 会话，并有成功交付的位置/身份依据；不凭正文、时间接近、相同文件名、相同 URL 或 Bot UID 推断。
- 对应模型执行已正常耗尽且明确 completed，输出属于其成功 final；failed/cancelled/unknown、只有中间片段或仅有 session.update 均不作为排除依据。成功投递 ACK 与模型完成分别核实，先后竞态不能让资格提前生效。
- 消息确实被已有 assistant 内容覆盖。正常 final 及其确定性关联的同一产物文件卡可作为候选；包含额外业务事实、独立文件、交付失败说明、后续编辑或无法核对的内容保留。Gateway 改写路径产生的 URL 不按相同 URL 自动合并，未改变的普通历史链接原样保留。
- 本轮若发生新会话回退，不会使用排除后的历史。Gateway 必须先证明这一点；不能等 fresh_fallback 事件到达后，仅标记下一轮补位就认为本轮没有丢失。

任何一项无法证明，保留该消息。一个候选不明确不应导致同段其他用户消息被删除。Provider 的压缩事件或语义不明的句柄变化也不能用来肯定旧正文仍完整，保守保留；不新增压缩监听或读取 Provider 私有历史。

## Gateway 内的实施方式

优先最小改动：复用已有 binding、turn/Run 和输出位置记录，通过少量适用条件与逐消息位置筛选解决普通接续场景。以下检查点用于防止误删，不要求新增一套历史管理或通用输出账本。已有证据不够时直接保留，不为扩大过滤覆盖率增加复杂状态；恢复路径无法沿现有 Gateway 装配安全处理时，同样不启用排除。内部字段如确有必要，以最小补充为限，不预设必须新增。

1. **保留原始候选。** 从同一次有界 sync 结果准备历史，先保持原消息位置、ID及次序；不直接按发送者过滤，不追加请求、分页或扩大历史窗口。
2. **关联已完成输出。** 在现有 turn/Run、执行终态和最终投递观察处核对归属；仅保存本项所需的有界元数据，仍计入原 binding 容量与 TTL，不保存正文历史库。不得把所有 `own=true` 或旧 `localOutputSeqs` 自动升级为可排除凭据。缺信息或超容量退回保留。
3. **选择正常接续历史。** 满足全部条件才在 Gateway 排除具体记录。实现先对完整原窗口执行既有格式化和预算，再拆为主历史与恢复材料，避免过滤后回填扩大取材量。原“全部是自己输出”无请求快速路径已移除：ACK 不足以核对内容编辑，也不能准备本轮回退材料。
4. **核实恢复输入。** 检查现有 Gateway 的 `freshFallbackModelInput/Parts` 和规则恢复装配，必要时在 Gateway 内为同一冻结材料准备未经过本项排除的恢复版本。恢复版本仍按原窗口/预算处理并保留 query、图片、稳定说明和群规则，不能出现主输入与恢复输入两套 history 拼接后重复或冲突。准备不了安全恢复输入时保留主历史，不改 Adapter 或 Core 来补救。
5. **保守推进状态。** 正常交接、已确认覆盖、真正缺失和预算省略分开判断；主动排除不等于 API 返回空，更不构成其他消息已交接的证据。实际缺失仍保留 pending 边界和 note。只排除已覆盖输出不产生 note、不触发模型重跑或历史重读。
6. **冻结与失效。** 排队在开始准备时读取本代次最新状态；同代次重试沿用冻结选择与恢复版本。reset、fresh fallback、Provider 句柄变化、失败/未知和进程变化使排除资格失效，迟到 ACK 不能写入新代次。元数据缺省按无证据解释，不建立升级兼容流程。

实现复用 turn token，在源流正常耗尽且 completed 后、final 投递前附上 Provider ID。仅成功 final 正文及其产物文件卡的投递观察记录消息序号和 SHA-256 内容指纹；记录按 Provider 分区、最多 32 条，并沿原 binding 容量和 TTL 淘汰。控制消息、交互/进度、错误和交付失败提示没有该指纹。API 返回后同时核对自身 UID、具体序号和原 payload 指纹；被编辑或无法核对时保留。无新增通用“模型已读”账本或 Provider 能力注册表。

同一次读取先按原 20 条/8000 码点预算形成完整窗口，再按序号分为互不重叠的主历史和恢复历史。恢复历史经模型历史投影去除内部元数据，沿现有 `freshFallbackModelInput/Parts` 补充给本次 fresh fallback；Core/Adapter 无改动。只有主历史实际进入快照时才加入恢复部分，同代次重试保存两者。

## 风险与保守降级

| 风险 | 必须采取的策略 |
| --- | --- |
| 同 UID 的旧会话消息误删 | 逐消息核对会话/代次/Run/Provider 归属，未知保留 |
| 补位原本要找回的消息被删 | 补位整体禁用本项排除，保留自身消息 |
| 执行时恢复失败，新会话拿不到旧回复 | Gateway 内保证冻结恢复版本；保证不了则不排除，不等待下一轮修补 |
| 文件卡包含 assistant 未有的新信息 | 未证明同一 final 的重复交付表示就保留，不做通用 URL/内容去重 |
| 筛选引发假缺失、游标前移或无限补读 | 分别核对 API 覆盖、实际交接与主动排除，按既有 pending 语义验证 |
| 重试、reset、淘汰和迟到事件串会话 | 身份校验及有界失效，沿用冻结输入，旧事件不产生新资格 |

## 后续验收矩阵

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| CH-01 | 用户原例：创建 MD、Bot 文件卡+正文、未触发的冷笑话消息、再 mention | 明确连续接续时只补冷笑话消息；当前 mention 在 query |
| CH-02 | 首次进入已有群/子区，历史中含自身 Bot | 原窗口内自身文件卡与回复均保留，不因同 UID/URL 删除 |
| CH-03 | reset/new 后再触发 | 新会话保留旧 Bot 历史，旧代次 ACK 不生效 |
| CH-04 | 读取失败、预算省略后补位，或 pendingAfterSeq 为 number/null | 补位保留自身消息，不据残留排除凭据删除 |
| CH-05 | 正常 delta 混合用户、其他 Bot、自身旧会话及本会话回复 | 只排除明确覆盖的本会话具体输出，其余原顺序保留 |
| CH-06 | 同 Bot 的错误/控制消息、交互卡、独立工具发送、后续编辑或不确定文件卡 | 保留，不从 own 标记、类型或 URL 推断 assistant 已有 |
| CH-07 | Provider 会话变化、compacted/恢复不明、重启、TTL/容量淘汰、store 能力缺失 | 保留；证据缺失导致重复而非漏历史 |
| CH-08 | 模型 failed/cancelled/unknown、completed 后源流异常、ACK 与终态先后交错 | 不产生可提前使用的排除资格，不误推其他消息边界 |
| CH-09 | resume 先成功但首次提交失败后 fresh fallback；无其他 gap、只有自身输出 | 新会话取得未经过本项排除的窗口历史；无法保证则本轮不排除、不错误跳过读取 |
| CH-10 | 只有已覆盖输出被排除，另有真实缺失/截断的对照 | 前者无假 note，后者保持 note 与待补状态 |
| CH-11 | 自动重试/卡片重试、排队与 reset 竞态 | 完整冻结快照和恢复输入保持，旧事件不修改新会话 |
| CH-12 | 引用/转发中含自身发言，或宿主显式 history | 嵌套内容及显式 Context 不作本项排除 |
| CH-13 | 历史上限、8000 码点、总 Context 预算及多模态恢复 | 不扩请求范围，不静默丢业务项，恢复输入无重复 history |

实施专项显式手动运行，复用现有历史、session、重试、产物交付与三 Provider 输入 fixture；不新增默认测试 glob、CI job 或 Gate。真实接口和模型验收另记证据，不以 fixture 声称已验证 Provider 完整记忆。

## 实施前检查

- 明确哪些现有终态和交付回执能够在 Gateway 内构成最小归属证据，确认无请求快速路径也受同一规则约束。
- 确认现有恢复输入在三种 Provider 路径的消费语义和预算，尤其覆盖 CH-09；未确认的路径默认保留，不为通过验收修改 Adapter。
- 复核状态提交/失败补位/冻结重试，不将已发送或已准备误写成模型已保存。

实施前单独评估为 96/100，见 assessment.md；没有继承原稳定 Context 功能的 97/100 准备度。实现、review、构建/安装与人工验收边界见 [验证记录](validation.md)。当前未声称真实 Provider 长期记忆完整性已经实测。
