# 目标

结构化合同见 [spec.yaml](spec.yaml)，A1–A9 的逐项证据见[验证记录](validation.md)，远端审查处理见[审查记录](review.md)。

将 [Issue 193](https://github.com/Mininglamp-OSS/octo-runtime/issues/193) 作为职责判断案例写入架构规则及 docs：模型目录由 Provider 及实际后端定义，来源与选项展示归接入宿主；Runtime 负责显式执行输入的原生适配和真实结果，不建立统一模型/effort 目录服务。

本规格取代[初始分诊](triage.md)中“建议 P2 新增模型目录 API、贯通 Go/Python 绑定”的建议。用户已明确要求更新规格、架构约束和 docs，本次直接落地文档，不修改产品代码。

## 背景与需求价值

用户在应用中选择模型需要可靠选项，这是宿主的产品需求。原 issue 将消费者缺少选项来源推导为 Kernel 应新增公共目录接口，未充分证明数据来源及责任归属。

同一个 Codex 等 Provider harness、Adapter 和版本，可连接官方服务、第三方代理站或自定义 endpoint；模型 ID、别名、默认值、权限和推理选项可能随后端和账号变化。执行协议兼容不保证有模型枚举接口，官方目录不能代表所有代理后端。某个 CLI 有没有查询命令或某个版本有没有协议方法，不是永久架构前提。

因此，不提供统一目录不等于不能执行显式模型，也不等于 Runtime 必须弥补 Provider 的查询缺口。先判断职责，再决定是否需要新增接口，不能因现有代码没有方法就推导为功能缺陷。

## 已确认决策与关键合同

| 决策                                | 约束                                                                                                                                                      |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1 Provider 拥有原生事实            | Provider harness 和实际服务/代理后端定义模型标识、可选查询接口和执行接受/拒绝；不要求其必须支持枚举                                                       |
| D2 宿主拥有接入及选项来源           | 宿主选择 endpoint、账号和配置，决定后端查询、管理员配置或用户输入等来源，管理刷新、失败、缓存与展示；本次不设计宿主目录服务                               |
| D3 Runtime 拥有执行适配             | 按现有合同映射显式输入、执行必要原生校验并返回真实结果；不维护统一目录、静态兜底或模型权限推断                                                            |
| D4 不补造发现能力                   | 不为选择器新增 Kernel IPC/Adapter metadata/Go/Python 目录合同，不扫描私有凭据、不额外登录或准备认证、不创建探测会话或发送推理请求来填补目录               |
| D5 不改变选模合同                   | 保留显式模型传递和省略默认语义；没有自建目录不导致拒绝有效调用；CodeBuddy 等本次执行会话中的原生目录校验和模型确认仍须保留                                |
| D6 区分 effort 语义                 | 原生可选值、Runtime 已实现映射和本次应用结果分开判断；现有四挡映射及未应用提示不变，不据目录建立动态准入或隐藏选择器                                      |
| D7 区分目录状态和执行状态           | 目录不可得、查询失败及成功空结果由宿主按实际来源解释，不伪造空成功，也不将目录不可得等同于 Runtime 执行不可用                                             |
| D8 两种业务传递路径均与 Kernel 无关 | 宿主直接查询/传递，或 Extra 调用宿主注入的 dependency；Extra 可选，函数可自定义或复用 Provider 集成，不要求 Provider 新增扩展机制，不增加 Kernel 业务 RPC |

后续某个 Provider 新增原生目录接口，宿主可以按实际集成需求使用，不自动授权扩展 Runtime 公共合同。通用能力注册中心的既有禁令继续有效。

## 经典扩展场景：Provider dependency 供 Extra 使用

用户最新明确：重点是模型目录及业务数据传递与 Kernel 无关。宿主可以直接查询 Provider 或向外部服务传递数据，无需 Extra；也可以由 Extra 调用宿主注入的 dependency 完成查询或传递。两条路径都不经过 Kernel，Extra 是可选方式。

采用 Extra 路径时，具体 Extra 定义业务函数合同，宿主自行实现 lambda 或复用 Provider 集成模块的函数，再选择并注入；不要求 Provider 新增 dependency 扩展机制。函数在 Extra 所在进程运行，可查询所配置的代理后端，也可将目录或其他业务数据发往外部服务。

当 Extra 已定义并消费依赖时，用户只需提供实现，无需扩展 Kernel 或通用 Adapter。没有消费入口时，不能仅传入一个同名函数就宣称已有 Extra 支持该功能；本次仅文档示例，不增加实际查询/发布依赖方法。

宿主负责配置、凭据与授权；业务合同定义输入、输出、错误、取消/截止及有副作用操作的发送、重试和确认语义。现有框架负责注入、实际在途和关闭管理，不自动注入 signal，不重试外部写操作。函数不进入 JSON、不经 Kernel IPC 传递，不要求暴露 worker 中的 Adapter 实例，不新增 Provider dependency 注册中心。

## 架构范围核对

1. 真实业务动作是用户选择模型；选项来源需要真实、可解释，价值成立。
2. 数据事实归 Provider/实际后端，接入配置和展示归宿主，执行映射归 Runtime/Adapter。
3. Runtime 接收现有显式模型/effort 输入，不额外选择、继承或改写产品默认值。
4. 无统一目录首先是产品来源或后端查询合同问题，不是 Kernel 执行合同被违反；缺少 IPC 方法不构成 Runtime 应兜底的证据。
5. 不改变其他宿主的展示、默认值、会话及配置，不创建查询生命周期。
6. 本次没有新增自动发现、降级、重试、缓存或安装动作；宿主策略的实现不在本次范围。
